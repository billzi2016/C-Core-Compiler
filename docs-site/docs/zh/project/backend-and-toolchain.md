# 后端与系统工具链

## 后端到底在做什么

到了后端阶段，前面的工作基本已经把程序逻辑整理清楚了。

后端的任务不是再重新理解语义，而是把前面准备好的结果，转成一种真正能继续构建的目标代码。

当前项目里，这个目标代码不是原生汇编，而是规范化 C。

## 为什么先输出 C

这件事值得反复强调，因为它决定了整个项目第一代的形态。

输出规范化 C 的好处包括：

- 可以立刻借助系统编译器生成可执行文件
- macOS 和 Linux 上都更容易工作
- 中间产物更容易人工阅读
- 不用马上处理 ABI、汇编语法和目标文件细节

所以这个后端更像一个“可执行的桥接层”。

## 当前后端其实也有两种模式

### 1. IR Backend

如果程序走基础 `int` 子集路径，后端读取的是 IR。

此时它会把每条 IR 指令翻译成较直接的 C 语句，例如：

- `const` -> 常量赋值
- `copy` -> 普通赋值
- `binary` -> 二元表达式
- `jump` -> `goto`
- `cjump` -> `if ... goto ... else goto ...`
- `return` -> `return`

这一条路径的特点是：控制流已经被前面的 lowering 展开好了。

### 2. AST Backend

如果程序用了 `char`、字符串、数组、指针等扩展特性，后端读取的就是 AST。

此时它不是按 IR 指令翻译，而是直接把 AST 重新渲染成 C 结构，例如：

- 指针声明
- 数组声明
- 下标访问
- 字符串字面量

这条路径保留了更多高层语言结构。

## 什么叫“规范化 C”

这里的“规范化”不是文学意义上的优雅，而是工程意义上的规则和稳定。

例如：

- 生成形式尽量统一
- 局部变量和临时变量显式声明
- 控制流直接展开
- 输出风格更利于检查和测试

也就是说，后端代码首先是“便于编译器自己维护”，其次才是“像人手写的漂亮 C”。

## 为什么系统工具链仍然不可少

即使后端已经生成了 C，项目本身还没有直接产出最终可执行文件。

最后这一步仍然需要系统工具链来完成，例如 `clang` 或 `cc`。

它们负责处理：

- 真正的 C 编译
- 目标文件生成
- 链接
- 平台相关细节

这正是 `toolchain.py` 的职责范围。

## ToolchainDriver 在做什么

当前 `ToolchainDriver` 主要做三件事：

1. 选择后端并生成后端文本
2. 把生成结果写到中间 `.generated.c` 文件
3. 调用系统里的 C 编译器，产出最终可执行文件

这里把中间文件落盘非常重要，因为：

- 构建失败时可以直接检查生成代码
- 方便用户理解“编译器到底生成了什么”
- 有利于回归测试和手工调试

## 为什么这条设计很适合第一代

如果第一代就直接做原生汇编后端，需要同时解决：

- 指令选择
- 寄存器分配
- 调用约定
- 栈帧管理
- 平台差异

这会让项目复杂度暴涨。

而当前设计把复杂度拆开了：

- 先把前端和中间层做扎实
- 再用规范化 C 先跑通执行链
- 以后如果需要，再把后端替换成更底层实现

这是一种非常合理的工程节奏。
